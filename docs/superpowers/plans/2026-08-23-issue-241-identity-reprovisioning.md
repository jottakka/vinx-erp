# Issue #241 Identity Reprovisioning Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

**Goal:** Recover the same exact internal VINX user after an out-of-band hard deletion and recreation in Supabase Auth, without e-mail-based identity linking or inherited authorization.

**Architecture:** An offline PlatformBootstrap command verifies that the expected old provider subject is absent and the exact new subject is valid, then invokes one migrator-only SECURITY DEFINER function. The function rotates the existing external-identity row in place, revokes internal sessions, advances the user session barrier, and appends a redacted audit event atomically.

**Tech Stack:** .NET 10, Supabase Admin REST through the existing verifier, EF Core/PostgreSQL migrations, Npgsql, PlatformBootstrap, xUnit/Testcontainers.

## Global Constraints

- Implement the approved policy at https://github.com/jottakka/vinx-erp/issues/241#issuecomment-5386662307.
- Reprovision only the same explicitly targeted internal user; never lookup, resolve, or attach by e-mail.
- Require exact user ID, expected old issuer/subject, and new subject from validated server-side configuration.
- Old subject must be absent; new subject must be valid/confirmed; provider e-mail is only a secondary equality guard against the already selected internal user.
- Preserve the same user, external-identity ID, memberships, roles, capabilities, employee records, and platform-operator FK; revoke every active internal session and advance sessions_valid_after.
- Expose no HTTP API, frontend, direct SQL runbook, service-role credential, generic user lifecycle, or invitation-acceptance behavior.
- Reuse SupabaseAdminUserVerifier and existing migrator/identity-owner/audit/session patterns; add no package or provider SDK.
- Use strict RED → GREEN TDD, compact Portuguese docs, safe outcome-only output, and never access quality/private.
- Keep manual lines at or below 800. Generated migration designer/snapshot lines are reported separately. If the plan exceeds the limit, remove nonessential harness/CI work instead of broadening the PR.
